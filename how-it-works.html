faultwall  /  how it works

How FaultWall sits between your agents and their APIs, MCP servers and databases.

A gateway runs next to your agent and holds the real keys for its APIs and MCP servers. For Postgres, FaultWall's Postgres proxy holds the database login. The agent uses a FaultWall key instead of the real one, and each call is checked against your rules, then allowed, blocked, or held for someone on your team.

01  Where it runs

It runs next to your agent, and keeps the real keys.

The gateway runs on the same server as your agent, or in the same pod. It listens only on that machine. The real keys stay with the gateway, and the agent gets a FaultWall key.

CALL PATH

Agent to gateway to service. Your agent code changes only where it sends calls and the key it sends, plus a retry for a held call that's approved after the wait. Run the gateway as its own OS user, so the agent can't read the real keys.

CONTROL PATH · IN PILOT

Company rules come down about every 30 seconds and, by default, can only make the gateway's own rules stricter. Literal-free stats go up, like POST /v1/refunds held, then approved. No keys, no argument values. Leave it off and nothing leaves the box.

APPROVALS

A held API or MCP call is approved on the gateway's own approval page, where the approver sees its values. That page is on the gateway's machine, or behind your own proxy or VPN. For those calls the website shows that a call is waiting and who to ask, and has no approve button. The Postgres proxy's held writes are approved on your side too, through the proxy's approval API.

02  Connecting an agent

Point the agent at FaultWall. Give it a FaultWall key.

# API: same call, the gateway's base URL, a FaultWall key
curl https://api.stripe.com/v1/charges -u <stripe-key>:
curl http://127.0.0.1:8443/stripe/v1/charges -u <agent-key>:

# MCP over HTTP: the client talks to the gateway
http://127.0.0.1:8444/mcp/<server>
Authorization: Bearer <agent-key>

# MCP over stdio: launch mcp-wrap where the server went
"command": "/usr/local/bin/faultwall",
"args": ["mcp-wrap", "--server", "fs",
         "--socket", "/run/faultwall/mcp.sock"],
"env": {"FAULTWALL_AGENT_KEY": "<agent-key>"}

# Postgres: swap one connection string, to the proxy
postgres://app_user:<db-password>@db.internal/orders
postgres://support-agent:<agent-key>@fw-proxy/orders
  1. Mint a key on the gateway. faultwall gateway keys add --agent billing-bot shows it once. Only its hash goes in policies.yaml. Postgres agents connect to the proxy with their own key instead of the database password.
  2. Give it rules for each service. Allow, block, or hold for a person, per agent and per API, MCP server or database. The real keys stay with FaultWall (the gateway, or for Postgres the proxy), never in the agent's config.
  3. Point the agent at FaultWall. The FaultWall key goes where the provider key went, so its SDK, MCP client or Postgres driver needs no code change. Postgres is tested with psql, pgx, psycopg 2 and 3, SQLAlchemy, asyncpg and node-postgres. If a call you hold is approved after the wait, the agent sends the same call again. With Stripe's SDKs, send a stable Idempotency-Key or turn off automatic retries, or each retry is held as a new call.
  4. Watch first. Start with --mode monitor: calls your rules would block or hold go through and are logged. Unknown keys are still refused, and on the gateway so are agents with no grant. Watch-only monitoring is free.
  5. Revoke on the gateway. Remove the key from policies.yaml and reload. Its open MCP sessions and its calls in flight end at once.

05  What we're building

    
Two pieces past allow and block.

    
Rules answer whether an agent may make a call. These answer what a query will do to the database right now, and what happens outside FaultWall.

Today: the scorer runs in FaultWall's Postgres proxy in shadow mode. It scores and records, and never blocks. We'll tune it on real workloads before it acts on anything. API and MCP calls get a fixed risk class instead: a refund is money going out. Illustration above, not partner data.

The gateway sees what goes through it. eBPF sees what actually runs.

    • 
          
  • Attributes CPU and disk I/O to each query using kernel scheduler and block I/O tracepoints.
    • 
          
  • Catches queries on connections that never went through FaultWall.

06  Fair questions

    
You may not need us. Here's how to tell.

    

      
The proxying part is ordinary. What's on top is the point. FaultWall classes each call by what it does: a refund is money going out, a file move is destructive. Today that covers Stripe-style payments and file tools; other APIs are classed by method. A held call waits for a person, and an approval covers that one call only; sent again, it waits again. It covers MCP tool calls too, including stdio servers it runs itself, so, with the gateway as its own OS user, their credentials never run as the agent. And faultwall suggest reads what each agent actually did and proposes tighter rules. You apply them; it never edits your rules.

      
You can, and some teams already run a shared approval service. FaultWall enforces where calls leave for the API, the MCP server or the database, so you get one set of controls without adding approval logic to each agent.

      
Then keep them. FaultWall becomes relevant when you need controlled writes, reviewable exceptions, or one consistent workflow across agents and services.

      
Yes. The gateway becomes part of the path to every service it covers. So we start in staging, watch-only first, and test compatibility, latency, failure behavior and recovery with your workload before you decide anything.

      
Measured on one machine over loopback, against local mock services and a local Postgres, on our MVP build of Nov 8. With one client, the median added time was 0.39 ms per API call, 0.10 ms per MCP call over HTTP, 0.16 ms over stdio and 0.10 ms per Postgres query. The 99th percentile was 2.3 ms per API call and under 0.5 ms for the others. With more clients at once it rose: 6.0 ms per API call with 16 clients, 1.0 ms over stdio and 0.7 ms per Postgres query with 4. The machine was busy, and the pilot build hasn't been measured yet. Real-network numbers come next.

      
If the gateway stops, the calls it protects stop too: the agent holds only a FaultWall key. Calls waiting for approval are denied when it shuts down cleanly. If the FaultWall website is unreachable, the gateway keeps enforcing the last company rules it checked, for as long as you allow, from 1 minute to 72 hours. Past that, calls under company rules are refused until it syncs again, and agents on local rules keep working. In our pilot run the website was down for a minute: a gateway set to one minute failed closed 60 seconds after its last good sync, then recovered by itself 10 seconds after the website came back, and no event was lost. Running the gateway highly available isn't built yet.

      
You pick which calls wait, such as refunds over $50. Everything else runs or is blocked by rule. During an evaluation we measure how many calls wait and how fast they're decided; a lot of repeats can mean a rule is too strict. Some operations should keep needing a person regardless. And one agent can have at most 16 calls waiting by default, so a looping agent can't bury your reviewers.
