faultwall  /  how it works

How FaultWall sits between your agents and Postgres.

A proxy runs in your network and speaks the Postgres wire protocol. Agents connect to it with their own key instead of the database password. It applies the rules you set in the FaultWall app to the statements routed through it.

01  Where it runs

Database traffic stays in your network.

You run the proxy next to your database. The FaultWall app holds agents, keys, rules and decisions. The two talk over a single outbound HTTPS connection that the proxy opens.

Agent to proxy to Postgres. Both connections stay inside your network. Your agent code doesn't change, only its connection string.

CONTROL PATH

The proxy pulls rules and sends held writes for review. In v0.7.0 reviewers see the statement shape, like UPDATE orders SET status = ? WHERE id = ?, not the values.

02  Connecting an agent

Swap one connection string.

# before: the agent holds the database password
postgres://app_user:<db-password>@db.internal/orders

# after: the agent holds only its FaultWall key
postgres://support-agent:<agent-key>@fw-proxy/orders

# check what each agent's DB user can do today
$ faultwall audit --fix
  1. Create the agent in the app. You get a key, shown once. Revoke it any time and the proxy refuses the next connection.
  2. Set its write rules. Allow, block, or hold for review, per agent.
  3. Point the agent at the proxy. Tested with psycopg2, psycopg3, SQLAlchemy, asyncpg and node-postgres. JDBC is not tested yet.
  4. Tighten the database side too. faultwall audit --fix generates the native Postgres privileges for each agent and lists the rules Postgres can't enforce on its own.

05  What we're building

    
Two pieces past allow and deny, built with design partners.

    
Rules answer whether an agent may run a statement. These answer what it will do to the database, and what happens outside the proxy. We're building both with design partners on real workloads.

    

      

        
Query world model
SHADOW MODE

        
Is this query allowed is one question. Will it slow production down right now is another.

        
    
          
  • Learns each query shape's own latency on a quiet database, from what it has actually observed, not the planner's estimate.
    • 
          
  • Samples live load from pg_stat_activity about once a second, off the query path.
    • 
          
  • Predicts latency under that load and flags queries likely to breach your latency target.
    •

Today: the scorer is in the proxy in shadow mode. It scores and records, and never blocks. We're tuning it on real workloads before it acts on anything. Illustration above, not partner data.

      

      

        
eBPF visibility
PROTOTYPE

        
The proxy sees what goes through it. eBPF sees what Postgres actually runs.

        
    
          
  • Hooks Postgres query start and finish with USDT probes, below the application.
    • 
          
  • Attributes CPU and disk I/O to each query using kernel scheduler and block I/O tracepoints.
    • 
          
  • Catches queries on connections that never touched the proxy.
    •

Today: working prototype, not shipped. Needs self-managed Postgres on Linux; managed services like RDS don't allow kernel probes. Until then, faultwall audit --fix covers the bypass case with native Postgres privileges.
