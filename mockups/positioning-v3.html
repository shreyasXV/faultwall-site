FAULTWALL  /  access control for AI agents on PostgreSQL  /  v0.7.0

Control what your AI agents can do in Postgres.

Give each agent scoped access. FaultWall enforces configured rules on operations routed through its proxy, lets permitted work proceed, and holds selected writes for an authorized reviewer. Review the decisions in one place.

§1 HOW IT WORKS

Define access once. Let the agent work inside it.

Most of what an agent does should just run. Review is for the exceptions you pick.

01

Create the agent in the app

Each agent gets its own key. Set which writes it can make and which ones wait for a reviewer. You can revoke the key at any time.

02

Point the agent at the proxy

The proxy runs next to your database. The agent swaps its connection string for the proxy address and its key. Only the proxy holds the real database password.

03

Permitted work proceeds

Reads and writes your rules allow go straight through. Operations your rules block, like DROP TABLE, never reach Postgres.

04

Selected writes wait for a reviewer

The write is held at the proxy before it reaches Postgres. Approve and it runs. Deny and the agent gets a clear error with your reason.

05

Review the decisions in one place

Every held write shows who approved or denied it and when.

§3 FAIR QUESTIONS

You may not need us. Here's how to tell.

We can build approval into our own tool layer.You can, and some teams already run a shared approval service. FaultWall enforces at the Postgres connection, so you can apply controls without adding approval logic to each agent implementation.
Scoped read-only roles already work for us.Then keep them. FaultWall becomes relevant when you need controlled writes, reviewable exceptions, or one consistent workflow across agents. Running faultwall audit --fix generates the privileges Postgres can enforce natively and lists the ones that still need FaultWall.
That's another component in production.Yes. The proxy becomes part of the database path. So we start in staging and test compatibility, latency, failure behavior and recovery with your workload before you decide anything.
Will engineers end up reviewing SQL all day?We measure approval volume and turnaround during the evaluation. A lot of repeat requests can mean a rule is too strict. Some sensitive operations should keep requiring review regardless.
§4 WHAT'S LIVE

What you can use now, and what we're building with design partners.

LIVE IN v0.7.0
  • Per-agent keys, issued in the app, revocable
  • Write rules set in the app: allow, block, or hold for review
  • Held writes wait at the proxy until approved or denied
  • Decision history with reviewer and outcome
  • Destructive operations blocked before Postgres sees them
  • faultwall audit --fix shows what each agent's DB user can do and generates native privileges
BUILDING WITH DESIGN PARTNERS
  • Shared policy across org, database and agent, with versions and rollback
  • Approvals in Slack
  • Policy preview: what a change would have blocked last week
  • Row limits on held writes
  • Query risk warnings before an agent query hurts production
  • Kernel-level detection of database access that skips the proxy
